Read failures are retriable only through a new bounded user submission. This is not a queue or automatic retry daemon. A pre-effect lease older than 60 seconds may be replaced atomically; request/fingerprint CAS prevents its old worker from sending. Inflight/external-effect/unknown states never become retryable just because time, provider idempotency TTL or process lifetime elapsed. A crash between the durable effect marker and network call remains conservatively parked, even if nothing was actually sent. Provider's existing bounded retries reuse the identical idempotency key and payload; no fresh operation is created on timeout/429/5xx after POST.

Pre-effect release is a recoverable warning; repeated occurrences warrant provider/DB investigation. These are code-level signals; no paid monitoring or Render configuration was added. Aggregate output has no addresses, tokens, hashes or provider payloads. Random operation IDs in error logs are correlation values, not derived from subscriber data. Scope-specific DB lookup requires privileged access; never expose it through anonymous HTTP.

## Render and rollout — HOLD, proposal only

Render's [documented deploy lifecycle](https://render.com/docs/deploys) sends SIGTERM to the old instance and defaults to **30 seconds** before SIGKILL; `maxShutdownDelaySeconds` can configure up to 300 seconds. The application uses at most 25 seconds (`API_SHUTDOWN_TIMEOUT_MS` can shorten it for tests). Actual production setting was not inspected or changed: Owner must verify it exceeds the app deadline plus margin. Safety does not depend on graceful shutdown succeeding. Both frontend/API currently auto-deploy main and API build runs migration, per Owner mandate.

1. **Before any merge:** independent exact-HEAD audit, Owner release authorization, DB owner global migration allocation/registry review, backup/restore approval, agreed lost-DOI policy. Auto-deploy/build migration is a live release mechanism, not a harmless repository action. No merge approval is implied by CI.
2. Resolve collision with contact-data CONTRACT 005 using read-only authorized migration-registry inspection. Keep existing applied checksums immutable. `candidates/005_newsletter_opt_in_requests.sql` is an unapproved historical filename, NOT an allocated next production migration. `newsletter_r4_expand_existing.sql` is an unnumbered proposal for installations already using R3's candidate. Neither is scanned by default migrations (001–004). Test helper is restricted to actual loopback `gracz_test` connections; Docker server bridge IP is not mistaken for a remote client.
3. Owner-approved maintenance window must **stop every old newsletter writer**, including contact-form opt-in and stale API instances. Merely pausing the new instance does not stop old code that lacks this switch. Verify routing, workers and outstanding provider operations drained or recorded uncertain. Default Render overlap is insufficient for this cutover. Hold public intake during the entire gap.
4. With old writers quiescent, take a consistent backup. Apply the separately approved additive schema proposal before unpaused new traffic. For existing R3 candidate preserve all `inflight`/`unknown` rows; never relabel them pre_send. Replay the idempotent historical import **after the final old-writer shutdown**, and verify counts/constraints/registry. Do not insert/edit migration registry entries to hide collisions/checksum differences.
5. Start new instances paused, verify explicit schema-ready health, proof/confirm/unsubscribe compatibility and privileged diagnostics without live test emails. Paused health is intentionally 200 even if candidate unavailable, with schemaReady false: deployment automation/Owner must inspect the flag before enabling intake.
6. Only after separate Owner GO start/resume unpaused R4 writers. Keep old writers stopped. No unsafe overlap. Existing API error/capacity validation and privacy-neutral request_received contract remain.
7. Rollback: pause/stop intake and retain additive schema, reservations and consent. Use a compatible paused version, never resume the old unreserved sender. Do not drop tables or reverse import. An Owner-controlled infrastructure rollback must account for auto-deploy on main; it is not executed by this PR.

## Retention, erasure and DR proposal — operational approval outstanding

- Explicit `purgeExpiredProofs()` deletes only status nonce/budget rows and completed public/status dispatch rows expired by >24 hours. Unexpired spent tokens remain replay tombstones. Token AEAD expiry independently rejects deleted expired nonces. No automatic cron/job is installed.
- B1 request rows, legacy/inflight/unknown/external-effect reservations and consent events are excluded. Do not use generic `expires_at` cleanup on these scopes: that could resend accepted mail. Indefinite safety holds need a separately approved legal retention/recovery decision, not silent deletion.
- Consent evidence is append-only, including failed pre-send request evidence. Owner/legal must establish purpose-specific evidence retention and lawful erasure exceptions. A verified erasure request first stops marketing/provider delivery, then follows an authorized, audited data procedure; no public erase endpoint, trigger bypass, wholesale ledger deletion or HMAC secret rotation is introduced. HMAC identifiers remain pseudonymous personal data.
- Backups must include newsletter contacts + immutable events + B1 reservations + **all** newsletter idempotency scopes + migration registry + constraints/triggers. Take a consistent snapshot; track backup boundary and provider operations after it. Restore to a separate isolated environment before switching any traffic.
- Losing post-backup consumed-token tombstones can resurrect still-valid proof. Losing consent/withdrawal events can permit stale confirmation. Therefore keep the API offline during disaster recovery, reconcile post-backup operations/withdrawals against authoritative provider and trustworthy logs, preserve unknown holds, and quarantine proof handling at least until all pre-restore 10-minute STATUS_CHECK envelopes expire. Intake pause alone is NOT sufficient for this quarantine. Longer DOI/withdrawal evidence requires reconciliation or continued HOLD, not a ten-minute guess.
- Escrow `NEWSLETTER_SECRET` and `NEWSLETTER_CONSENT_HASH_SECRET` separately in an Owner-controlled encrypted vault with access audit and tested recovery. Match key versions to backup; losing the HMAC key breaks subject correlation and replacing it can bypass dedup. Do not rotate keys to escape holds. No secrets were accessed or changed for this task.
- Disaster drill: `integration/newsletter-dr-fixture.mjs seed` creates synthetic records on validated loopback gracz_test only; dump via PostgreSQL16 pg_dump and restore via psql ON_ERROR_STOP into a second disposable instance; `verify <restored-url>` compares exact rows for five tables/registry and tests unknown DOI, ambiguous dispatch, consumed proof and immutable-event trigger. This is a logical backup/restore drill, **not** production PITR or proof of the production RPO/RTO. Production backup and escrow validation remain Owner gates.

## Lost or expired DOI — decision requested at release gate

Current behavior blocks an unexpired pending request; expiry of a definitely `sent`/`legacy_pending` request permits one fresh user-initiated DOI. An uncertain request stays held regardless of expiry. There is no immediate “resend” bypass. Owner must approve this retained policy or separately authorize a cooldown/mail-budget design for lost links; more permissive reissue increases mailbox spam risk. No policy decision or new resend feature is assumed here.
