# 1. Purpose

GFPE-2 defines the first precise protocol draft for generating, committing, freezing, consuming and verifying a FairPlay deck/shoe.

This document is deliberately more exact than GFPE-0/1, but it is **not yet an implementation specification freeze**.

No code may claim compliance until:

1. P8 is closed,
2. full-project audit is complete,
3. blocking findings are remediated,
4. Claude reviews this protocol,
5. Gemini reviews the bounded-sampling/statistical model,
6. Lead explicitly freezes a protocol version.

---

# 2. Non-negotiable protocol properties

- `NO FAIRPLAY = NO DEAL`.
- No `Math.random()` or game-local RNG for FairPlay card order.
- One immutable hand/session context.
- Fresh per-hand/server entropy.
- Commitments precede reveal.
- No participant changes committed contribution after observing later contributions.
- Final shuffle key is deterministic from canonical transcript.
- Shuffle is deterministic Fisher-Yates with unbiased bounded sampling.
- Frozen deck/shoe cannot be modified after commitment.
- Deal cursor is monotonic.
- Restart never regenerates an active deck/shoe.
- Stale node cannot deal from superseded ownership epoch.
- Idempotent retry cannot consume a second position.
- Proofs bind to protocol version, game rules version, build and key identity.

# 3. Canonical identifiers

Each FairPlay session/hand must bind at least:

```text
fairPlaySessionId
handId
matchId
tableId
shoeId?         // required for shoe-based games
roundId?
gameType
gameRulesVersion
protocolVersion
proofFormatVersion
buildGitSha
```

Rules:

- identifiers are immutable after session creation,
- `handId` cannot be reused after COMPLETE or ABORT,
- identifiers are part of the canonical transcript,
- aliases/user-facing names never replace canonical `gameType`.

# 4. Algorithm suite — DRAFT

Proposed first suite:

```text
hashAlgorithm       = SHA-256
commitAlgorithm     = SHA-256
kdfAlgorithm        = HKDF-SHA-256
prfAlgorithm        = HMAC-SHA-256
signatureAlgorithm  = Ed25519
secretAtRest        = AES-256-GCM where required
canonicalEncoding   = RFC 8785 JCS or frozen byte-equivalent canonical format
shuffleAlgorithm    = Fisher-Yates + rejection sampling
```

No custom hash/KDF/signature primitive is permitted.

Any substitution requires a new protocolVersion or explicitly versioned algorithm suite.

---

# 5. Domain separation

Every hash/HMAC/KDF use must include an explicit ASCII/UTF-8 domain label.

Draft labels:

```text
GFPE/COMMIT/PLAYER/v1
GFPE/COMMIT/SERVER/v1
GFPE/TRANSCRIPT/v1
GFPE/SEED/v1
GFPE/PRF/v1
GFPE/DECK/v1
GFPE/LEAF/v1
GFPE/PROOF/v1
GFPE/LEDGER/v1
GFPE/CHECKPOINT/v1
```

A value created under one domain must never be valid under another domain merely because raw bytes are identical.

---

# 6. Entropy requirements

## Server entropy

- generated from OS CSPRNG,
- fresh per hand/session or shoe according to adapter semantics,
- minimum target: 256 bits,
- never derived only from timestamp, UUID, counter or predictable metadata,
- must not be reused across hands.

## Player entropy

For commit/reveal-capable clients:

- fresh random contribution per hand,
- recommended 256 bits,
- generated by platform CSPRNG,
- client identity/seat is bound into commitment context,
- absent/invalid reveal is handled by explicit protocol state, never by silent substitution after commitment.

---

# 7. Commitment format — DRAFT

Player commitment draft:

```text
playerCommit = SHA256(
  domain("GFPE/COMMIT/PLAYER/v1") ||
  canonicalBytes({
    fairPlaySessionId,
    handId,
    gameType,
    gameRulesVersion,
    protocolVersion,
    playerId,
    seat,
    contributionNonce,
    playerSeed
  })
)
```

Server commitment draft follows same model with server-specific domain and server identity context.

Important:

- exact canonical byte format must be frozen before implementation,
- `playerSeed` and nonce remain secret until reveal phase,
- commitment record itself is durable before later phase advances.

---

# 8. Protocol state machine

Proposed states:

```text
CREATED
COMMIT_OPEN
COMMIT_CLOSED
REVEAL_OPEN
REVEAL_CLOSED
SEED_DERIVED
DECK_FROZEN
DECK_COMMITTED
DEALING
COMPLETED
ABORTED
```

No backward transition is allowed except read-only recovery of already persisted state.

Every transition is versioned and persisted atomically with its relevant protocol event.

---

# 9. Commit phase

1. Create immutable hand/session context.
2. Persist `SESSION_CREATED`.
3. Generate server entropy.
4. Persist server commitment.
5. Open player commitment window if adapter/policy requires it.
6. Accept at most one canonical commitment per required participant/seat unless protocol explicitly versions replacement-before-close behavior.
7. Close commitment phase durably.

No reveal is accepted before corresponding valid commitment exists.

---

# 10. Reveal phase

For each participant contribution:

1. receive seed + nonce,
2. reconstruct commitment bytes exactly,
3. hash under correct domain,
4. compare to committed digest using constant-time comparison where applicable,
5. persist verified reveal,
6. reject mismatch fail-closed.

A mismatched reveal MUST NOT be replaced with a different contribution.

Missing reveal handling requires explicit policy before freeze. Candidate policies include:

- abort hand,
- predefined contribution-neutralization scheme committed in advance,
- server-only mode for game classes where player entropy is not required.

No silent “generate replacement random seed now” fallback is permitted.

---

# 11. Canonical transcript

The final seed derivation transcript must be deterministic and order-stable.

Draft structure:

```json
{
  "protocolVersion": "GFPE-1.x",
  "gameType": "thousand",
  "gameRulesVersion": "...",
  "fairPlaySessionId": "...",
  "handId": "...",
  "server": {
    "commit": "...",
    "reveal": "..."
  },
  "players": [
    {"seat": 0, "playerId": "...", "commit": "...", "reveal": "..."},
    {"seat": 1, "playerId": "...", "commit": "...", "reveal": "..."}
  ]
}
```

Player array ordering is canonical by seat, then stable player identifier as tie-breaker only if a malformed state would otherwise be ambiguous.

Canonical transcript hash:

```text
transcriptHash = SHA256(
  domain("GFPE/TRANSCRIPT/v1") || canonicalBytes(transcript)
)
```

# 12. Shuffle-key derivation

Draft derivation:

```text
IKM = serverSeed || orderedPlayerSeeds || transcriptHash
salt = SHA256(domain("GFPE/SEED/v1") || canonicalContextBytes)
info = canonicalBytes({
  protocolVersion,
  gameType,
  gameRulesVersion,
  fairPlaySessionId,
  handId,
  purpose: "shuffle-key"
})
shuffleKey = HKDF-SHA-256(IKM, salt, info, 32)
```

Before freeze, Claude must review:

- concatenation/canonicalization ambiguity,
- whether seed values should be length-prefixed separately,
- salt/info construction,
- treatment of optional/missing player entropy,
- memory-zeroization expectations for server-side secrets.

---

# 13. Deterministic PRF stream

Draft block generation:

```text
block_i = HMAC-SHA-256(
  shuffleKey,
  domain("GFPE/PRF/v1") ||
  canonicalBytes({handId, counter: i})
)
```

Counter:

- unsigned monotonic integer,
- starts at frozen protocol-defined value,
- no counter reuse for different sampling requests under same stream unless deterministic byte-stream consumption is fully specified.

Preferred implementation model: deterministic byte stream with explicit cursor, so all implementations consume identical bytes.

---

# 14. Uniform bounded sampling

For required bound `n` where valid outputs are `0..n-1`, naive `random % n` is forbidden unless mathematical proof shows no bias for exact source width/bound.

Draft rejection method for an unsigned `w`-bit integer source:

```text
M = 2^w
limit = M - (M mod n)
repeat:
  x = nextUnsignedWBits()
until x < limit
return x mod n
```

The exact `w`, endianness and byte consumption must be frozen and cross-language tested.

Gemini independent review is required specifically for this section.

---

# 15. Fisher-Yates shuffle

For canonical deck array of length `L`:

```text
for i = L-1 down to 1:
    j = uniformInt(0, i)
    swap(deck[i], deck[j])
```

Requirements:

- canonical pre-shuffle deck ordering is versioned by game adapter/rules version,
- all implementations produce identical permutation from same test vector,
- no retry/resample except bounded-sampling rejection,
- no game-specific post-shuffle mutation.

---

# 16. Frozen deck / shoe representation

After permutation:

```text
state = DECK_FROZEN
```

Persist at minimum:

- canonical card sequence or encrypted authoritative equivalent,
- deck length,
- deck hash/commitment,
- cursor = 0,
- protocolVersion,
- gameRulesVersion,
- shuffle algorithm ID,
- transcriptHash,
- keyId/build identity.

Once committed:

- sequence immutable,
- cursor only increases,
- no duplicate position consumption,
- no arbitrary position skip unless adapter rule explicitly consumes/burns that position and records event.

---

# 17. Deck commitment

Minimum v1 commitment draft:

```text
deckCommitment = SHA256(
  domain("GFPE/DECK/v1") ||
  canonicalBytes({
    protocolVersion,
    gameType,
    gameRulesVersion,
    handId,
    deckCodes
  })
)
```

For privacy-sensitive games such as Poker, public disclosure of `deckCodes` is not permitted during active/private lifecycle.

A separate selective-reveal Merkle structure may coexist with private authoritative full-deck commitment.

---

# 18. Selective reveal / Merkle direction — Poker DRAFT

For each position `p`:

```text
leaf_p = SHA256(
  domain("GFPE/LEAF/v1") ||
  canonicalBytes({handId, position:p, cardCode, leafSalt})
)
```

Merkle root commits to ordered leaves.

Selective reveal may disclose:

- position,
- cardCode,
- leafSalt,
- Merkle proof.

This proves membership of revealed card/position in committed tree.

It does **not** by itself publicly prove that all hidden leaves form a complete unbiased permutation. That stronger property remains outside v1 unless a separately reviewed verifiable-shuffle/ZK design is adopted.

# 19. Authoritative deal

A deal operation must bind:

```text
handId
matchVersion / expectedVersion
ownershipEpoch
idempotencyKey
startingCursor
consumeCount
adapterOperation
```

Examples of adapter operations:

- `DEAL_PRIVATE_CARD`
- `BURN_CARD`
- `DEAL_COMMUNITY_CARD`
- `DEAL_MUSIK`

The transaction must guarantee:

- expected state/version still current,
- current ownership epoch,
- requested cursor equals persisted cursor,
- positions consumed exactly once,
- updated cursor/state committed atomically with deal event,
- idempotent replay does not consume additional positions.

---

# 20. MatchRuntime integration

GFPE should not create a second independent concurrency authority.

Target integration:

```text
MatchRuntime command
  -> GFPE validates protocol state / cursor
  -> GFPE applies deterministic deal transition
  -> PostgreSQL transaction/CAS
  -> committed authoritative state
  -> viewer-safe projection
  -> signal-only realtime
```

`ownershipEpoch` and `expectedVersion` remain outer authoritative fencing inputs.

# 25. Verify Hand

Verifier responsibilities:

- validate proof schema/version,
- validate signature/key identity,
- validate checkpoint/hash-chain evidence supplied,
- validate revealed card proofs,
- validate public commitments,
- where full seed/deck disclosure is legally/privacy-safe, reproduce transcript → seed → shuffle → deck,
- report limitations for hidden information.

Possible output statuses:

```text
VERIFIED
VERIFIED_WITH_PRIVATE_ELEMENTS_NOT_PUBLICLY_DISCLOSED
INVALID_PROOF
UNSUPPORTED_PROTOCOL_VERSION
INSUFFICIENT_DISCLOSURE
```

Avoid generic boolean `fair=true` if verification coverage is partial.

---

# 26. Abort protocol

Abort is a durable terminal state.

Record at minimum:

- handId,
- phase,
- reasonCode,
- commitments already present,
- reveals already present,
- transcriptHash if available,
- node/build/key context,
- matchVersion / ownershipEpoch,
- timestamp.

Rules:

- handId never reused,
- abort record never deleted to hide an unfavorable entropy outcome,
- new hand gets new identity and fresh entropy,
- abort frequency becomes statistical/audit signal.

---

# 27. Restart / recovery

On restart:

1. load persisted GFPE session,
2. verify protocol state consistency,
3. verify deck commitment/integrity,
4. verify cursor bounds,
5. verify match ownership/version context,
6. do not regenerate entropy/deck,
7. continue only from persisted legal state.

Corruption or impossible state => fail closed + audit event, not auto-repair by reshuffle.

# 29. Tysiąc adapter constraints

First validation adapter should define:

- canonical 24-card ordered deck,
- game rules version,
- seat ordering,
- initial hand distribution,
- musik/talon positions,
- whether all cards are consumed at start or progressively,
- private/public reveal policy,
- reconnect projection,
- end-of-hand proof disclosure.

No independent RNG is allowed for musik/talon.

# 30. Poker adapter constraints

Poker adapter later must define:

- 52-card canonical deck,
- seat/dealer/button semantics,
- private hole positions,
- burn positions,
- flop/turn/river positions,
- folded/mucked privacy,
- selective proof disclosure,
- end-of-hand reveal policy,

Historical poker deck/evaluator code is reference only until reuse audit.

# 31. Blackjack adapter constraints

- shoe identity and deck count versioned,
- one frozen shoe per lifecycle,
- monotonic cursor across hands,
- reshuffle only at explicit legal cut/termination point,
- no per-hand reshuffle fallback.
